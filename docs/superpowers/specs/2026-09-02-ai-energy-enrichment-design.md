# 车型能源 AI 补全功能设计

## 1. 背景与目标

神州租车上游接口只能为部分车型提供可靠的新能源线索，现有车型库仍有大量“能源未知”记录。车型变化频率较低，逐项人工标记成本高，适合使用用户自行配置的 OpenAI 兼容接口进行批量补全。

本功能的目标是：

1. 在系统设置中配置任意 OpenAI 兼容接口。
2. 从车型库手动启动后台批量补全任务。
3. 补全能源大类和能源细分类型。
4. 高置信结果自动写入车型库，不确定结果保持未知。
5. 全城车型和车型库同步显示同一份生效结论。
6. 保留任务、调用和车型修改历史，支持停止、继续和失败重试。

## 2. 本期范围

### 2.1 补全字段

- 能源大类：`燃油`、`新能源`、`未知`。
- 能源细分：`汽油`、`柴油`、`纯电`、`插电混动`、`增程`、`油电混动`、`其他`、`未知`。
- 置信度：`高`、`中`、`低`。
- 判断依据：简短中文文本。
- 参考来源：模型返回的来源说明或链接列表；无可靠来源时允许为空。

AI 不修改神州车型 ID、车型名称、原始描述和图片。

### 2.2 明确不做

- 不增加逐车型人工能源下拉框。
- 不增加 Excel 导出、AI 填写和回导流程。
- 不增加定时执行；所有任务由用户手动触发。
- 不依赖 Responses API 或内置网页搜索。
- 不补全排量、驱动方式、座位数、年代等其他车型字段。

## 3. OpenAI 兼容接口配置

设置页面新增“AI 补全”二级页面，配置保存在现有 `integration_settings` 表中，服务提供者标识为 `openai_compatible_enrichment`。

配置项：

- 启用开关。
- API Key：作为密钥保存，读取接口只返回脱敏值。
- Base URL：用户自行填写，例如 `https://api.deepseek.com`。
- 模型名称：用户自行填写，不在代码中固定模型列表。
- 单批车型数：默认 15，允许 1 至 30。
- 请求超时：默认 90 秒，允许 10 至 300 秒。
- 最大重试次数：默认 2，允许 0 至 5。

“测试 API”发送一个最小 `/chat/completions` 请求，并验证：

- 密钥、地址和模型可用。
- `response_format={"type":"json_object"}` 能返回合法 JSON。
- 返回内容满足最小字段约束。
- 展示响应耗时和 Token 用量。

API Key 不出现在日志、错误详情、HTML 和客户端响应中。

## 4. 数据模型

### 4.1 车型当前状态

在现有 `vehicle_models` 表上保留并扩展能源字段：

- `energy_type`：当前生效的能源大类。
- `energy_subtype`：当前生效的能源细分。
- `energy_source`：`MANUAL`、`AI_FOCUSED`、`AI_BATCH`、`UPSTREAM` 或空。
- `energy_confidence`：`HIGH`、`MEDIUM`、`LOW` 或空。
- `energy_updated_at`：当前能源结论的更新时间。

现有 `energy_type` 和 `energy_source` 原值保持不变；新增字段初始为空。

生效优先级为：

`人工确认 > AI 单车复核 > AI 批量判断 > 神州描述推导 > 未知`

后续扫描不得覆盖 `MANUAL`、`AI_FOCUSED` 或 `AI_BATCH` 来源的有效能源结论。

### 4.2 AI 补全任务

新增 `vehicle_enrichment_runs` 表：

- 任务编号。
- 处理范围：`PENDING_ONLY` 或 `ALL`。
- 状态：等待、运行、停止、完成、部分完成或失败。
- 使用的 Base URL 脱敏标识和模型名称。
- 总数、已处理数、已更新数、仍未知数、失败数。
- 第一阶段请求数、第二阶段请求数。
- 输入 Token、输出 Token、总 Token。
- 创建、开始、停止和完成时间。
- 最近错误摘要。

同一时间只允许一个活动任务，重复点击返回当前活动任务，不创建并发任务。

### 4.3 单车型补全结果

新增 `vehicle_enrichment_results` 表：

- 所属任务和车型内部 ID。
- 处理阶段：批量判断或单车复核。
- 状态：等待、处理中、已应用、保持未知、失败。
- AI 建议的大类、细分、置信度、依据和参考来源。
- 修改前后的能源字段和来源。
- 是否应用及未应用原因。
- API 请求次数、Token 用量和错误摘要。
- 创建和更新时间。

任务重试更新同一任务下的车型结果，不重复创建成功记录。新任务保留新的历史行。

## 5. 补全流程

### 5.1 选择车型

默认“补全待处理车型”选择以下任一情况：

- 能源大类为空或未知。
- 能源细分为空或未知。
- 当前置信度为低。

“重新识别全部车型”作为二级操作，选择所有车型，但人工来源记录仍不会被覆盖。

### 5.2 第一阶段：批量判断

系统按配置的批量大小发送车型数组，每项包含：

- 神州车型 ID。
- 车型名称。
- 神州原始描述。
- 当前能源大类、细分和来源。

提示词要求返回 JSON 对象，其中包含与输入一一对应的车型结果数组。系统执行严格校验：

- 返回的车型 ID 必须存在于本批输入中。
- 每个输入 ID 最多返回一次。
- 枚举值必须在允许范围内。
- 大类与细分必须一致，例如纯电不能归入燃油。
- JSON 缺失、截断、重复或非法结果按该批失败处理。

批量结果为高置信度时直接应用；中、低置信度或未知进入第二阶段。

### 5.3 第二阶段：单车复核

系统对待复核车型逐个发送更完整的聚焦提示，要求模型重新判断并说明依据。本期不调用网页搜索工具，只使用用户配置的 OpenAI 兼容 `/chat/completions` 接口。

第二阶段只有高置信度且通过一致性校验的结果才写入车型库。其余结果记录为“保持未知”。

### 5.4 自动写入规则

- AI 结果只能更新能源相关字段。
- 人工来源永不被 AI 覆盖。
- 第一阶段高置信结果写入来源 `AI_BATCH`。
- 第二阶段高置信结果写入来源 `AI_FOCUSED`。
- 未达门槛时保留原值；原值为空时继续显示“能源未知”。
- 每次应用前后的字段都保存到结果历史中，支持后续审计和回滚扩展。

## 6. 页面与交互

### 6.1 设置页面

新增“AI 补全”设置页，包含配置表单、脱敏密钥状态、测试结果和清除密钥操作。测试失败时显示安全的中文错误，不返回上游响应原文中的敏感内容。

### 6.2 车型库

车型库顶部新增主按钮“AI 补全车型信息”。默认创建 `PENDING_ONLY` 任务。

默认收起的更多操作包含：

- 重新识别全部车型。
- 查看 AI 补全记录。

当前或最近任务以紧凑进度区显示：

- 状态和处理进度。
- 已更新、仍未知、失败数量。
- 当前阶段、请求数和 Token 用量。
- 停止、继续、重试失败项和刷新操作。

车型列表能源列显示“大类 · 细分”，并以弱化文字显示来源；未知时只显示“能源未知”。

### 6.3 全城车型

全城车型不增加任务入口，读取相同的车型能源字段，显示与车型库一致的“大类 · 细分”和来源，避免两个页面同时启动任务。

### 6.4 AI 补全记录

新增独立记录页面，分页展示历史任务。展开任务可查看失败和保持未知的车型、错误摘要、Token 用量及结果依据，不在车型库首屏堆叠明细。

## 7. API 设计

设置接口：

- `GET /api/settings/integrations`：增加 AI 补全配置摘要。
- `PUT /api/settings/integrations/openai-compatible`：保存配置。
- `DELETE /api/settings/integrations/openai-compatible/secret`：清除密钥并停用。
- `POST /api/settings/integrations/openai-compatible/test`：测试接口。

任务接口：

- `POST /api/vehicle-enrichment-runs`：创建任务，参数为处理范围。
- `GET /api/vehicle-enrichment-runs`：分页读取历史任务。
- `GET /api/vehicle-enrichment-runs/{run_id}`：读取任务进度和统计。
- `POST /api/vehicle-enrichment-runs/{run_id}/stop`：停止。
- `POST /api/vehicle-enrichment-runs/{run_id}/resume`：继续。
- `POST /api/vehicle-enrichment-runs/{run_id}/retry-failed`：重试失败车型。

所有接口使用严格请求模型和中文错误信息，并登记到现有系统 API 台账页面。

## 8. 任务执行与容错

- 后台执行复用现有应用生命周期任务模式，不阻塞 HTTP 请求。
- 每批事务独立提交，单批失败不回滚已成功批次。
- 网络超时、限流和临时服务错误按配置次数重试。
- 非法 JSON、空内容、枚举冲突和 ID 不匹配记录为可重试失败。
- Docker 重启后运行中任务标记为中断，可由用户继续。
- 停止操作在当前 API 请求结束后生效，不中断已经发送的请求。
- API 未配置、未启用或测试失败时禁止创建补全任务。

## 9. 测试与验收

必须覆盖：

- 配置保存、脱敏、清除和测试。
- API Key 不出现在响应和日志中。
- 批量 JSON 正常、空内容、截断、重复 ID、未知 ID 和非法枚举。
- 大类与细分一致性校验。
- 高置信自动应用，中低置信进入复核，复核仍不确定则保持未知。
- 人工来源不会被 AI 或扫描覆盖。
- 默认范围和全量范围选择正确。
- 并发任务拦截、停止、继续、失败重试和重启恢复。
- 两个车型页面同步显示相同结果。
- 任务记录、统计、Token 用量和分页。
- Docker 构建、数据库迁移和健康检查。

## 10. 实施顺序

1. 数据库迁移和领域模型。
2. OpenAI 兼容客户端与结构化结果校验。
3. 设置接口、页面和测试连接。
4. 补全任务服务、执行器和任务 API。
5. 车型库按钮、进度和记录页面。
6. 车型库与全城车型能源展示同步。
7. API 台账、中文文档、全量测试和 Docker 部署。
