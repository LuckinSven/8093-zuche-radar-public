# 广州按车型反向找车设计

## 1. 目标

系统继续以广州为中心，并把首页的两个核心用途明确分开：

1. **广州全城车型扫描**：用户选择一个租期，手动遍历广州网点，扩充车型库并查看该租期的全城车型。
2. **按车型找车**：用户从永久车型库选择一款或多款车型，手动启动任务。系统自动采样未来四个周末的多个时间窗口，反向找出这些车型在哪些准确租期和网点可取。

“按车型找车”关注车型，不要求用户先选择取车网点。鱼珠地铁站只作为距离计算和排序基准。

本次继续使用现有 FastAPI、Jinja、原生 JavaScript、CSS 和 PostgreSQL，不引入新的前端框架，不增加自动定时任务。

## 2. 已确认的产品规则

1. 所有扫描均由用户手动触发。
2. 首页默认功能是广州全城车型扫描。
3. 鱼珠附近快速扫描缩小并合并到全城扫描卡片底部，默认收起。
4. 首页原“找车条件”改成真正的“按车型找车”，不再只是过滤旧数据。
5. 找车目标必须从永久车型库中搜索和选择，不接受车型库之外的自由文本目标。
6. 一次任务可以选择多款车型。
7. 同名但神州车型 ID 不同的细节车型全部参与，并在结果中分别展示。
8. 不预选取车网点；神州返回的实际 `deptId` 作为候选可取网点。
9. 首版按广州同城取还理解；系统不声称已经确认具体异店还车网点。
10. 默认扫描未来四个周末。
11. 每个周末先扫描周六 09:00 到周日 09:00，以及周六 09:00 到周一 09:00。
12. 同一个手动任务在基础扫描后继续执行小时精扫。
13. 小时精扫覆盖周六 08:00 至 20:00，每小时一个取车时间；还车时间同步平移，分别维持 24 小时和 48 小时租期。
14. 任务只保存和展示实际请求过的时间组合，不推断未采样时段。
15. 2000 次请求是警告阈值，不是截断上限；5000 次是单任务硬上限。

## 3. 页面结构

### 3.1 首页

首页按以下顺序布局：

1. **广州全城车型扫描**
   - 取车时间、还车时间。
   - 启动按钮和当前任务的紧凑进度。
   - 卡片底部放置默认收起的“鱼珠附近快速扫描”。
2. **按车型找车**
   - 可搜索的车型库多选框。
   - 已选车型以可移除标签展示。
   - 默认说明“未来 4 个周末、08:00–20:00 小时采样、24/48 小时租期”。
   - 创建前展示预计请求数及预计执行方式。
   - 启动按钮和最新任务的紧凑进度。
3. **最近扫描汇总**
   - 只展示少量统计和进入结果、扫描记录的入口。

首页不再展示原“找车条件”筛选区。原有网点、能源、车身、价格等筛选能力放在全城车型结果页和对应任务结果页。

### 3.2 扫描记录

现有扫描记录页面增加两个清晰的页签：

- 全城扫描。
- 按车型找车。

按车型找车的每条记录显示：目标车型、计划样本、成功、失败、待处理、请求数、已发现车型变体数、可取网点数、创建和完成时间，以及完整性状态。运行中的任务支持停止；已停止或部分完成的任务支持继续。

### 3.3 按车型找车结果

结果使用三级列表：

1. 车型名称。
2. 实际采样租期。
3. 神州车型变体和可取网点。

默认只显示至少有一个有效可租结果的车型和租期。页面可切换显示未找到或扫描不完整的项目。

每项结果显示：

- 车型名称。
- 神州车型 ID、原始描述等变体信息。
- 准确取车和还车时间。
- 24 小时或 48 小时租期。
- 可取网点。
- 网点距鱼珠的直线距离。
- 有效报价的均价、最低价和最高价；价格标注为非最终结算价。
- 最近验证时间。
- 完整、扫描不完整或未找到状态。
- 现有个人标签和车型详情入口。

相邻小时均返回可租时，页面可以折叠显示为“连续采样可租”，但展开后必须列出每个准确采样时间，不能表达为未经验证的连续库存。

网点区域明确提示：“可取网点来自神州接口返回；还车范围按广州同城处理，具体还车网点请在神州 App 确认。”

## 4. 扫描流程

### 4.1 目标解析

用户选择的是车型库中的车型名称。创建任务时保存名称和当时匹配到的全部神州车型 ID 快照，避免执行期间车型库变化导致任务范围漂移。

多款车型共用一次上游响应。系统不能为每款目标车型重复发送相同请求。

### 4.2 基础扫描

系统生成未来四个周末共 8 个基础租期：

- 每周六 09:00 → 周日 09:00。
- 每周六 09:00 → 周一 09:00。

每个租期遍历任务创建时的广州有效网点快照。按当前约 91 个网点估算，基础扫描约需 `8 × 91 = 728` 次上游请求。

基础扫描有两个用途：

- 寻找目标车型当前实际出现的网点。
- 继续更新永久车型库；同一响应中的非目标车型不进入本任务结果，但仍可更新车型库的名称、描述、最近发现等信息。

### 4.3 候选网点

小时精扫使用以下网点的并集：

- 目标车型历史上曾返回过的可取网点。
- 本次基础扫描新返回的可取网点。

多个目标车型共享并集并按神州网点 ID 去重。鱼珠仅用于结果排序，不限制候选集合。

### 4.4 小时精扫

对每个候选网点和未来四个周末，采样周六 08:00 至 20:00 的整点。每个取车时间分别请求 24 小时和 48 小时租期，还车时间与取车时间同步平移。

基础扫描已经覆盖 09:00，因此同一任务不重复请求该精确组合。除去 09:00 后，每个候选网点最多增加：

`12 个额外小时 × 2 种时长 × 4 个周末 = 96 次请求`

请求预算按所有目标车型共享后的候选网点并集计算，而不是按车型数相乘。

### 4.5 缓存和去重

精确请求键包含：

- 城市。
- 查询网点或查询坐标的稳定标识。
- 取车时间。
- 还车时间。
- 影响上游结果的其他请求参数版本。

规则如下：

1. 同一任务内，相同请求键只执行一次。
2. 不同任务间，成功结果在完成后 2 小时内可以复用。
3. 超过 2 小时的结果重新请求，因为车辆可租状态具有时效性。
4. 失败、超时、被停止和格式异常的结果不得作为成功缓存复用。
5. 复用缓存时仍在任务中记录“缓存命中”，保证进度和结果可追溯。

## 5. 请求预算与执行策略

创建任务前计算预计请求量：

`未命中的基础请求 + 未命中的小时精扫请求`

由于候选网点只有基础扫描后才能完全确定，创建时同时展示历史估算值和说明；基础扫描结束后更新最终计划数。

- 预计不超过 2000 次：最多 2 个上游请求并行。
- 超过 2000 次：自动降为 1 个请求串行执行，以降低上游压力；任务可以运行更久。
- 超过 5000 次：拒绝进入小时精扫，不静默截断。页面提示用户减少车型或周末范围后重新创建。

对连接错误、超时、上游 5xx 和明确的限流响应采用有上限的指数退避。业务拒绝和返回格式不兼容不盲目重试。

点击停止后立即停止调度新请求；正在执行的请求允许结束并保存。继续任务时只处理未完成和允许重试的样本。

## 6. 状态与可信性

任务状态包括：

- 等待中。
- 基础扫描中。
- 小时精扫中。
- 已完成。
- 部分完成。
- 已停止。
- 预算超限。

结果状态遵循以下规则：

- **可租**：某个准确采样请求成功，且返回目标车型的可预订报价。
- **未找到**：计划范围内所有相关样本均成功完成，但没有返回该目标车型。
- **扫描不完整**：存在待处理、停止或最终失败样本。此时不能把没有返回解释为无车。

任务可以在已有成功样本上展示可租结果，即使整体为部分完成。错误信息保存安全摘要，不展示上游响应正文、内部地址或敏感信息。

## 7. 数据保存

新增按车型找车的任务、计划样本和标准化结果数据：

- 任务保存 60 天。
- 每个精确样本的执行状态、请求元数据、缓存来源和安全错误摘要保存 60 天。
- 目标车型的标准化可租结果和价格保存 60 天。
- 不长期复制保存每次精扫的完整上游大响应。
- 永久车型库继续只增加、不删除；扫描可更新上游标签和最近发现时间，但不得覆盖人工信息和更高可信来源。
- 非目标车型仅更新永久车型库，不保留为该找车任务的详细结果。

超过 60 天的找车任务和明细由现有维护流程分批清理。永久车型库、人工标签和车型首次发现时间不受影响。

## 8. 接口设计

新增系统接口：

- `POST /api/model-search-runs`：创建按车型找车任务。
- `GET /api/model-search-runs`：分页读取任务记录。
- `GET /api/model-search-runs/{id}`：读取任务计划、进度和统计。
- `POST /api/model-search-runs/{id}/stop`：停止任务。
- `POST /api/model-search-runs/{id}/resume`：继续任务。
- `GET /api/model-search-runs/{id}/results`：分页读取三级聚合结果。
- `GET /api/model-library/options`：为多选框搜索车型库名称和对应变体数量。

创建接口使用车型库中的稳定车型选择值，并保存匹配到的 ID 快照。所有写接口拒绝多余字段，返回中文错误。新接口同步登记到“系统设置 → API 接口台账”，使其他 ChatGPT 对话可以按文档调用。

## 9. 性能与交互

- 车型多选采用服务端搜索，不一次加载完整车型库。
- 结果在 PostgreSQL 中聚合、筛选、排序和分页。
- 车型行按需加载租期，租期按需加载变体和网点，避免一次返回全部明细。
- 任务运行时只轮询轻量进度接口；页面不可见时暂停轮询。
- 首页进度更新只替换进度区域，不重绘整个页面。
- 任务结果页面使用现有清新、低干扰配色和统一字号，不增加悬浮筛选框。

## 10. 测试与验收

### 10.1 自动化测试

- 未来四个周末的日期计算，包括跨月和跨年。
- 08:00–20:00 小时采样及 24/48 小时同步平移。
- 09:00 基础请求与精扫请求正确去重。
- 多车型和同名多变体正确解析，不重复请求。
- 历史网点和本次网点并集正确去重。
- 两小时跨任务缓存命中、过期、失败结果不复用。
- 2000 次并发降级和 5000 次硬上限。
- 停止、继续、退避、部分完成和预算超限状态。
- 只有完整扫描才能得出“未找到”。
- 非目标车型只更新永久车型库，不混入任务结果。
- 结果三级分页和按需展开。
- 首页布局、扫描记录页签和 API 台账入口。
- 60 天清理不删除永久车型库和人工数据。

### 10.2 手工验收

1. 首页默认显示广州全城车型扫描，鱼珠快速扫描在卡片内默认收起。
2. 从车型库搜索并同时选择多款车型。
3. 启动前能看到请求量估算；超过 2000 次时明确提示任务将降低速度。
4. 启动后能看到基础扫描、小时精扫和整体进度，并可停止、继续。
5. 结果按车型、租期、变体和网点展开，准确显示取还时间和距鱼珠距离。
6. 任一失败样本使相关否定结果显示为“扫描不完整”，不会错误显示“未找到”。
7. 扫描记录可以分别查看全城扫描和按车型找车。
8. 系统设置的 API 接口台账包含新接口的请求参数、响应字段和示例。

## 11. 非本次范围

- 自动定时扫描和消息推送。
- 任意车型自由文本搜索。
- 全国或广州以外城市的按车型找车。
- 任意取车小时与任意还车小时的笛卡尔积扫描。
- 保证异店还车或指定还车网点。
- 预约、下单、登录和 Cookie 自动化。
- 根据未采样小时推断连续可租。
